## 09:10–10:35 — Separate declarations from consumption

The first design problem was semantic. Each frozen plan record already declares
what a future scientific execution will consume. An interface test still needs
to preserve that allocation so routing errors are visible, but copying the
allocation into a result could falsely look like work performed.

I made the distinction explicit. Every stub record carries both
`declared_future_consumption`, which must exactly match the frozen plan, and
`actual_consumption`, which must contain all protocol counters at zero. The
mode is fixed to `STUB_INTERFACE_TEST`, and `scientific_verdict` must be
null. Thus a test cannot label M01 killed, report an SDK statevector, or consume
a formulation pass without being rejected.

The baseline routes through L1, L2, L3 and L4 in that exact order. Mutants route
only to the layer predeclared in the plan. L1 exposes named counters for encoded
states and reduced decisions. L2 reserves fields for phase alignment and
complex-state errors. L3 reserves probability and energy-error fields. L4
requires physical feasibility and auxiliary consistency to stay separately
named. In stub mode, all measurement counts are zero and all numerical fields
are null.

## 10:50–11:30 — SIMULATED NARRATIVE: fault-model decision

In a fictional methods discussion with the Inria software-testing role, the
decision question was whether an empty interface test should use a placeholder
such as zero error. The decision was no: numerical zero means a comparison was
performed and found exact agreement, while null means no observation exists.
That distinction prevents future aggregate reports from confusing absent
science with perfect science.

The second decision was to reject extra fields. A permissive dictionary could
allow a callback to smuggle in a result that the validator never checks.
Exact schema equality is deliberately rigid for protocol v1; an interface
change requires a versioned contract change.
