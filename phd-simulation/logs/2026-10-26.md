## 09:10–09:50 — SIMULATED NARRATIVE: supervisor contract review

In a fictional 40-minute Monday review, the Norway-setting software-
verification role challenged one design question: should the harness decide
whether a mutant was scientifically killed? The answer was no. The harness
should decide only whether work is authorized, retained and within budget. The
independent formulation, complex-amplitude, readout and application oracles
must remain responsible for the scientific verdict.

The review fixed four implementation rules. Provenance must be complete before
a directory is reserved. A passing baseline terminal must exist before any
mutant callback. Consumption must be recorded at attempt time rather than
completion time. Finally, duplicate run and mutant identities must fail without
changing earlier bytes. A failure gets an abort record, never a success
terminal.

## 10:05–12:10 — Implement the orchestration boundary

I added `mutation_harness.py` using only the Python standard library. It creates
an append-only pilot ledger, validates mandatory provenance, reconstructs
counters from persisted attempt events and atomically reserves each record
directory. The fixed caps are represented explicitly, including zeros for
searches and paid or hardware-facing operations.

The first implementation mistake appeared during review rather than execution:
it would have been tempting to count resources from completed result files.
That is wrong for the protocol. If a callback builds a circuit and then throws,
the circuit still counts. The implemented counter therefore reads attempt
events, which are written before the callback begins. This also means an
infrastructure retry requires a new identity and remains visible.

## 13:00–14:35 — Execute dry-run tests, not mutants

I wrote and ran twelve tests with temporary directories and synthetic stub

after declared formulation consumption and confirm that the attempted work
remains counted.

Boundary tests refuse an SDK request that would take the total above fifteen,
